# 引き継ぎ — /data が消える障害の真因 (2026-09-07)

**この文書は「確定」「推定」「撤回」を分けて書く。区別を消さないこと。**

---

## 真因 (ログで確定)

**AIC8800 ドングルが、同じUSBハブ上のSSDを叩き落としている。**

起動時のカーネルログ（時刻は起動からの秒）:

```
[2.161] usb 1-1.3: ELECOM ESD-EXS 接続             ← SSD、ハブのポート3、正常
[2.260] scsi 1:0:0:0: Direct-Access ELECOM ESD-EXS ← sda として認識、/data マウント成功
[6.572] usb 1-1.1: ドングル切断  (a69c:5723 Aic MSC)
[7.297] usb 1-1.1: 再列挙        (a69c:8d80 AIC Wlan)
[7.612] usb 1-1.1: また切断      → aicwf_usb_disconnect enter
[8.321] usb 1-1.1: また再列挙    (368b:8d83 AIC 8800D80)
[9.014] AICWFDBG: aicwf_usb_rx_complete need to wait for disconnect callback
[9.574] usb 1-1.3: stat urb: status -71            ← 0.5秒後、SSDが壊れ始める
        以降 -71 が続き、再列挙も失敗、data.mount が外れる
```

**ドングルが3回再列挙した0.5秒後に、必ずSSDが落ちる。** 両者は同じ VIA ハブ (2109:3431)
の別ポートに刺さっている。ドングルのドライバ (aic8800) の既知バグ
(初期化中に必ずUSB切断する / issue #183、9/5に特定済み) が、ハブごと巻き込んでいる。

**このドングルは動作していない。** wlan1 は生成されず、WiFiとしての価値はゼロ。
何の役にも立たないまま SSD を殺していた。

### /data が消えると何が起きるか (今回の症状はすべてこれ)

| 症状 | 理由 |
|---|---|
| TRIP がゼロにリセット | `trip_state.json` が `/data` にある。読めないのでゼロから開始 |
| 燃費・数値がおかしい | 給油間の燃料積算のベースラインが無い |
| 時計が巻き戻る | 時刻の保存先が `/data/state/timesync` |
| 過去の起動のログが消える | journal の永続化先が `/data/log/journal` |
| drive-verify / can-verify が failed | `RequiresMountsFor=/data` |

**較正データは無事。** アプリは起動時に保存先が無いことを検知して縮退モードに入り、
読み書きを一切しない (`internal/trip/tracker.go` の `checkStateDir` → `degraded`)。
**SSDの中身は上書きされない。**

## 実施した対処 (2026-09-07)

`/etc/modprobe.d/blacklist-aic8800.conf` を作成し、**下層へ永続化済み**
(`overlayroot-chroot` 経由。`/media/root-ro` は ro に復帰確認済み)。

```
blacklist aic8800_fdrv
blacklist aic8800_bsp
blacklist aic_load_fw
blacklist aic8800
```

**戻すとき**: このファイルを消して再起動（下層側も消すこと）。

### 未検証 — 次のエンジン始動で確認すること

```bash
lsmod | grep aic            # 何も出なければブラックリストが効いている
mount | grep /data          # マウントされていれば成功
journalctl -k -b 0 | grep -c ' -71'   # 0 なら SSD は無事
```

**成功なら、TRIP と較正値はアプリが自動で読み戻す。手で値を書く必要はない。**

## 内蔵WiFi の接続失敗 (別問題・未解決) — 2026-09-07 調査結果

### 確定したこと

**起動時の失敗は 100% ドライバ内部で完結している。AP は無関係。**

```
[23.313] wlan0: Trying to associate with 1c:7c:98:b5:46:91 (freq=2462 MHz)
[23.725] wlan0: CTRL-EVENT-ASSOC-REJECT bssid=00:00:00:00:00:00 status_code=16
```

- `bssid=00:00:00:00:00:00` = **AP から1フレームも返っていない**。この status_code=16 は
  AP が送ったものではなく、ドライバが自分で作った失敗報告
- 失敗は毎回 **380〜450ms**。電波のタイムアウト(秒単位)ではなく内部の即時エラー
- 全起動を通して、起動時の ASSOC-REJECT は **すべて全ゼロ BSSID**（実 BSSID は 0 件）
- 定常時(接続後の再接続)には実 BSSID の拒否も出るが、**それは別現象**

### ハードとファーム（`nmcli` の表示は誤り。カーネルが正しい）

```
brcmfmac: using brcm/brcmfmac43455-sdio for chip BCM4345/6
Firmware: BCM4345/6 wl0: Aug 29 2023 version 7.45.265 (28bca26 CY) FWID 01-b677b91b
```
**BCM4345/6 (CYW43455)、2.4/5GHz 両対応。** `nmcli` は `BCM43438` と表示するが誤り。
issue #34 の対象チップ (BCM4345) と一致する。

### 既知の推奨対策は「すでに完全に適用済み・有効」

```
/proc/cmdline               brcmfmac.feature_disable=0x82000   ← 届いている
/sys/.../parameters/roamoff 1                                   ← 有効
wpa_cli get_capability key_mgmt
  → NONE IEEE8021X WPA-EAP WPA-PSK WPA-EAP-SUITE-B OWE DPP FT-PSK FT-EAP
    **SAE が無い = SAE オフロードは無効化されている**
```
**「roamoff=1 を足せば直る」という筋は消えた。** 両方入っていて、なお直らない。

### 説明できていないこと — 起動ごとのばらつき

単調時間で、全起動を同じ物差しで測った結果:

```
boot -3:   22秒 / 全ゼロBSSID  0回
boot -2:   37秒 / 全ゼロBSSID  2回
boot  0:  632秒 / 全ゼロBSSID 46回
```
同じ設定・同じ場所・同じ AP で 22秒 と 632秒。**原因不明。**

計測コマンド（次回もこれで測ること。累計と1回分を混ぜない）:
```bash
journalctl -b <N> -o short-monotonic | grep -m1 CTRL-EVENT-CONNECTED   # 接続までの秒数
journalctl -b <N> | grep -c 'ASSOC-REJECT.*bssid=00:00:00:00:00:00'    # 起動時の失敗数
```

### 外れた仮説（同じ道を通らないこと）

| 仮説 | なぜ外れたか |
|---|---|
| AP の WPA3/PMF/省電力 | 起動時の失敗は全ゼロ BSSID = AP は無関係 |
| `roamoff=1` が抜けている | 既定で有効。SAE も実際に無効化済み |
| 2.4GHz 専用チップが 5GHz を掴もうとしている | チップは両対応。`nmcli` の型番表示が誤り |
| `set_channel fail -52` が原因 | 最初の6回の失敗(t=23〜65s)より**後**の t=79s から始まる |
| Pi の CPU 負荷 | 累計値と1回分を比べた誤り。機序も弱い(association はファーム側) |
| 省電力 (Pi 側 `powersave`) | 無効化して悪化。無関係 |
| 2.4GHz へのバンド固定 | 改善なし |

### ドングルとの相関（2026-09-07 測定・単調時間で統一）

```
boot   ドングル   初回試行   接続まで   ASSOC-REJECT
  0      あり      23s      632s      46
 -1      あり       -      到達せず      0
 -2      あり      23s       37s       2
 -3     なし       21s       22s       0    ← ドングル無しの唯一の起動
```

**ドングルが居ない起動は 1 回だけで、それが唯一の失敗ゼロ。**
AIC8800 のドライバは cfg80211 に登録される (`cfg80211 ... brcmfmac_cyw,brcmfmac,aic8800_fdrv`)
ので、USB を壊すだけでなく 802.11 スタックにも触っている。

**重要: ドングルを物理的に抜いた状態での起動は、2026-09-07 07:30 時点でまだ 1 回も無い。**
boot 0 も起動時点ではドングルが刺さっていた (t=6.5s で再列挙)。抜いたのはその後。

### ファーム差し替えについて — **やる理由なし。実施しないこと**

`/lib/firmware/cypress/` に2種類が入っていて `update-alternatives` で切替できるが、
**切り替えても何も起きない。**

```
brcmfmac43455-sdio.raspberrypi,4-model-b.bin   md5 64410bcb1364a794
cyfmac43455-sdio-standard.bin                  md5 64410bcb1364a794  ← 完全同一
cyfmac43455-sdio-minimal.bin                   md5 25e38143baafc917  ← 別物
```

brcmfmac は **基板専用ファイル** (`...raspberrypi,4-model-b.bin`) を優先して読む。
`update-alternatives` が指すのは、使われていない汎用シンボリックリンクのほう。
本当に minimal を試すなら基板専用ファイル自体を差し替える:

```bash
# 手順は docs/boot-resilience.md:101 のとおり overlayroot-chroot 経由
sudo overlayroot-chroot cp '/usr/lib/firmware/brcm/brcmfmac43455-sdio.raspberrypi,4-model-b.bin' \
     '/usr/lib/firmware/brcm/brcmfmac43455-sdio.raspberrypi,4-model-b.bin.bak'
sudo overlayroot-chroot cp /usr/lib/firmware/cypress/cyfmac43455-sdio-minimal.bin \
     '/usr/lib/firmware/brcm/brcmfmac43455-sdio.raspberrypi,4-model-b.bin'
```

**ファームは起動時に読まれる。外すと WiFi が死に、車内では戻せない。**

#### なぜ「やる理由なし」と結論したか（2026-09-07）

1. **4回の起動すべてで、ファームは同一 (standard)。** それでも boot -3 は
   22秒 / 失敗0回、boot 0 は 632秒 / 失敗46回。**ファームが原因なら
   boot -3 も失敗しているはず。** 犯人ではない
2. **WPA3(SAE)オフロードは既に `feature_disable=0x82000` で無効化済み**で、
   実際に効いている (`wpa_cli get_capability key_mgmt` から SAE が消えている)。
   ドライバが使っていない機能を持たないファームに替えても動きは変わらない
3. **「minimal が何なのか」は未確認。** ファイル名と上流のコミットタイトルからの推測。
   `strings` の比較でも意味のある差は出なかった ("MFP" が 3個 vs 2個 のみ)

**推測を根拠に、車内で復旧できない変更をしてはいけない。**
手順は上に残してあるが、これは「もし将来やることになったら」の参照用で、
現時点で実施する根拠は無い。

1. **接続のやり直しを短時間に繰り返す実験をしない。**
   2026-09-07 未明に2回実施し、2回ともPiをネットから失った。得られた情報はゼロ。

   `sudo systemd-run --on-active=180 --unit=xxx /path/revert.sh` (9/5に作成・動作確認済み)。

## 未完の作業 — 次に繋がったら最初にやる

**`wifidbg.sh` が `/boot/firmware` を rw のまま放置している。**
前夜のデバッグ用フック。起動45秒後に `mount -o remount,rw /boot/firmware` を実行し、
**ro に戻していない。** FAT のブートパーティションが rw のまま電断すると起動不能になりうる。
`cmdline.txt` の `systemd.run=` は編集しない（編集ミスが即起動不能）。スクリプト側を潰す:

```bash
sudo cp /boot/firmware/wifidbg.sh /boot/firmware/wifidbg.sh.bak
sudo tee /boot/firmware/wifidbg.sh >/dev/null <<'SH'
#!/bin/sh
# 2026-09-07 無害化。旧版は /boot/firmware を rw のまま放置していた。
mount -o remount,ro /boot/firmware 2>/dev/null
exit 0
SH
sudo sync && sudo mount -o remount,ro /boot/firmware
mount | grep boot/firmware   # (ro, で終わることを確認
```

緩和要因: fstab の `/boot/firmware` は fsck パス2 なので、起動時に自動検査される。
