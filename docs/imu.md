# IMU (GY-521 / MPU-6050)

勾配・横G・前後加速度を直接測るために 2026-09-06 に追加した。狙いと背景は
issue #165 にある。要点だけ再掲すると、勾配が無いせいで撤回した結論が2件あり、
横Gは数値化できておらず、加速度は5Hzの車速を微分するしかなかった。

GPS の標高でも勾配は出せるが、**トンネル内では原理的に取れない**。IMU は
どこでも効く。逆に IMU 単体では長距離のドリフトが避けられないので、
開けた場所では GPS の標高が独立した検証になる。

## 配線

Pi の 40 ピンヘッダに 5 本つなぐだけ。車体側の配線には触らない。

| GY-521 | Pi | |
|---|---|---|
| VCC | 1番 (3.3V) | **5V にしてはいけない。下記参照** |
| SDA | 3番 (GPIO2) | |
| SCL | 5番 (GPIO3) | |
| INT | 7番 (GPIO4) | **必須。下記参照** |
| GND | 9番 (GND) | 6・14・20・25・30・34・39番でも可 |

XDA / XCL / AD0 は未接続でよい。AD0 開放でアドレスは 0x68 になる。

CAN HAT は SPI (19・21・22・23・24・26番) を使うので競合しない。
ファンは 4番 (5V) と 6番 (GND) に刺さっている。

### VCC を 3.3V にする理由

GY-521 にはレギュレータが載っているので VCC に 5V を入れても石は壊れない。
問題は基板上の I2C プルアップ抵抗で、**どこに繋がっているかが個体によって違う**。

- レギュレータの後 (3.3V) → 5V を入れても信号は 3.3V。安全
- VCC の入口 (生の電圧) → 5V を入れると信号も 5V。Pi の GPIO が危ない

基板を追わないと区別できない。VCC に 3.3V を入れれば**どちらでも信号は 3.3V**
になり、問題自体が消える。MPU-6050 の動作範囲は 2.375〜3.46V なので正常な使い方。

### INT を必ず繋ぐこと

`inv_mpu6050` ドライバは**自前のトリガ (`mpu6050-dev0`) しか受け付けない**。
これはセンサーのデータレディ割り込みで駆動されるため、INT が未接続だと
バッファが一度もデータを吐かず、`/dev/iio:device0` の read が永久に止まる。

ソフトウェアトリガ (`iio-trig-hrtimer`) で代用しようとしたが、
`current_trigger` への書き込みが拒否された。2026-09-06 に実測で確認済み。

繋がっているかは割り込み回数で分かる。

```
$ grep inv_mpu /proc/interrupts
 56:  300  0  0  0  pinctrl-bcm2835  4 Edge  inv_mpu
```

バッファ有効中に 100Hz なら 3 秒で約 300 増える。0 のままなら未接続。

## 有効化

`/boot/firmware/config.txt` に2行。ドライバはカーネル内蔵の
`inv-mpu6050-i2c` で、外部ビルドは不要 (#183 のような苦労が無い)。

```
dtparam=i2c_arm=on
dtoverlay=i2c-sensor,mpu6050
```

`int_pin` は既定で GPIO4 なので指定不要。再起動すると
`/sys/bus/iio/devices/iio:device0` (name=mpu6050) が現れる。

## sysfs の1回読みを使ってはいけない

`in_accel_x_raw` のような1回読みは、**ドライバが読むたびにセンサーの電源を
入れ直す**。ジャイロは安定に時間がかかるため、過渡値を拾う。

2026-09-06 の実測では、静止しているのに3回の測定すべてで
X=-129, Y=-93, Z=-91 deg/s という同じ値が現れた。バッファ経由で連続取得したら
正体が分かった。

```
-128.90  -93.15  -90.77   ← 1サンプル目
-128.90  -93.15  -90.77   ← 2サンプル目
 -53.93  -89.19 -117.98
 142.63   32.64  -18.67
  15.13   -2.14   36.66
  -2.93    0.31    1.95   ← 6サンプル目で収束
```

起動直後の過渡値だった。加速度計は収束が速いので影響を受けず、
1回読みでも静止時 1G を正しく返す。**ジャイロだけが騙される。**

`imu-log.py` は起動後 100 サンプル (1秒) を捨てている。

## ロガー

`scripts/ops/imu-log.py` を `imu-log.service` から常時起動する。
IIO バッファを 100Hz で読み、`/var/log/imu/imu-MMDD-HHMM.csv`
(→ `/data/log/imu`、SSD) に書く。約 25 MB/時。

`/dev/iio:device0` は root でしか開けないので `User=` は付けていない。

列は `t,mono,ax,ay,az,gx,gy,gz,temp`。加速度は m/s²、角速度は deg/s、温度は ℃。

**`mono` は起動からの秒数。** 壁時計 (`t`) は NTP や GPS の同期で飛ぶため、
**経過時間の計算には必ず `mono` を使う**こと。詳細は
[boot-resilience.md](boot-resilience.md) の「時計が毎回巻き戻る」を参照。

## 取り付け

**車体に対して動かないこと**が唯一かつ最大の条件。向きは問わない。
静止時の重力ベクトルから取付角を求めて補正できるので、斜めでも逆さでもよい。
ただし一度決めたら動かさないこと。動くと較正がやり直しになる。

厚いスポンジ両面テープは避ける。バネのように働いてセンサーが独自に揺れる。
薄く硬いテープか、基板の2つの穴を使ったネジ留めが確実。金属ケースに直付け
するときは裏面のはんだが触れないよう絶縁すること。

## 解析と検証 (2026-09-06)

`scripts/ops/imu-analyze.py` が取付角を較正し、車両座標系での勾配・横G・
前後Gを出す。`scripts/ops/imu-grade-verify.py` がその勾配を GPS の標高変化で
独立に検証する。

### 手順

1. **停車中 (車速0) の平均加速度**が重力ベクトル。これで「下」が決まる
2. 重力に直交する平面へ射影し、**車速の微分と最も相関する向き**を「前」とする
3. 前後加速度から車速微分を引いた残差が `g·sinθ`。これが勾配
4. 「前」と「下」の外積が「横」。これで横Gが出る

### 車速の微分は 1 秒の窓で取ること

**走行ログは 5Hz (200ms間隔)** なので、IMU の 10ms 刻みでそのまま微分すると
補間誤差しか見えない。最初これをやって勾配が ±45〜57% という値になった。
窓を ±0.5秒 に広げ、勾配側に 2 秒の移動平均をかけると ±10% 以内に収まった。
**勾配は路面の凹凸よりはるかにゆっくり変化する。**

### 実測 (2026-09-06、20km・25分)

```
取付角     重力 X -8.708  Y -3.707  Z +1.279   大きさ 0.9738 G
勾配       中央値 -1.15%   5〜95%点 -3.76%〜+2.01%   最小 -9.80%  最大 +6.54%
横G        中央値 0.032 G  95%点 0.144 G  最大 0.631 G
前後G      最大加速 +0.243 G  最大減速 -0.293 G
```

### GPS 標高による検証

GPS の標高は誤差が数メートルあるので1点ずつでは使えない。60秒の窓で
「標高 対 走行距離」を直線近似し、その傾きを勾配として比較した。

```
20区間で比較
  相関係数    0.835
  差の平均   -0.69 %
  ばらつき    0.89 %
```

**相関 0.835 は、IMU が実際の道路勾配を追えていることを示す。**

差の平均 -0.69% は較正の前提から来る。**「停車中は水平」と仮定して重力の
向きを決めているため、停めた場所が傾いていればそのぶん全体がずれる。**
複数の停車地点で平均すれば消える。ばらつき 0.89% は GPS の標高誤差が
支配的で (1km あたり ±5m の誤差は ±0.5% の勾配に相当)、IMU 側の限界では
ない。

## 高速巡航では勾配の検証が通らない (2026-09-07・未解決)

那須高原→都賀西方 81.6km (中央値 105 km/h、94% が 80km/h 超) で GPS 標高との
相関が **-0.224**。9/6 の市街地走行は同じコードで **0.835 / 0.904** を再現するので、
**コードの問題ではない。**

```
             速度        60秒窓の距離   相関
9/6 市街地   〜25km/h    350〜500m      +0.835 (30s窓で +0.904)
9/7 高速     105km/h     1,600〜1,900m  -0.224 (30s -0.190 / 120s -0.169)
```

**窓幅を変えても回復しない** (15〜120秒で試験済み)。速度域そのものが効いている。

観測された内訳:
- GPS 実測の勾配は **±0.5〜1%** しか振れていない (平坦な高速道路)
- IMU 側は **±2〜4%** 振れている → ノイズが信号を上回っている
- ばらつき 1.60% (9/6 は 0.89%)
- 差の平均は +0.00% なので**オフセットではなく形が合っていない**

取付角の再較正そのものは正常に働いている (ケース再固定後も重力 9.5405 m/s² =
0.9729 G、9/6 の 9.5535 とほぼ同じ)。停車サンプルも 6,527 個で十分。

**未解決。** 2秒移動平均では高速域の振動を落としきれていない可能性があるが、
未検証。横G (最大 0.607 G) も同じ理由で裏が取れていない。

### 外れた仮説
- **検証窓が高速域に合っていない** → 15/20/30/60/120秒すべてで相関は負のまま

## 健全性の確認

静止させて合成加速度が 1G になるかを見る。

```
X = -8.750 ± 0.039  m/s^2
Y = -3.390 ± 0.038
Z =  1.794 ± 0.057
合成 9.5535 = 0.9742 G
```

2026-09-06 の仮止め時の値。**ばらつき (±0.04) が小さいことが固定できている
証拠。** 合成が 1.000 から 2.6% ずれているのは MPU-6050 の個体差の範囲
(軸オフセット ±50mg、感度誤差 ±3% が規格)。

**勾配の測定には実害がない。** 勾配は停車時の基準からの変化で測るので、
この誤差は勾配の値に比例してかかるだけ。5% の坂が 5.13% と出る程度。
